1 Quickstart

The whole idea, in one command: hand it some data, name a dialect, get SQL back.

Pass an inline JSON document and pick a dialect. With the -i / --inserts flag you also get the values loaded:

shell
$ ddlgenerator -i postgresql '[{"Name": "Alfred", "species": "wart hog", "kg": 22}]'
sql · postgresql
CREATE TABLE table0 (
	name VARCHAR(6) NOT NULL,
	species VARCHAR(8) NOT NULL,
	kg INTEGER NOT NULL
);

INSERT INTO table0 (name, species, kg) VALUES ('Alfred', 'wart hog', 22);

That is the entire loop. Note what it worked out on its own:

  • Types — Name/species became VARCHAR sized to the longest value; kg became INTEGER.
  • Nullable — every value was present, so each column is NOT NULL.
  • Identifiers — the messy "Name" header was normalized to lowercase name.
  • Table name — no file given, so it defaulted to table0. (From a file, it takes the file name.)
One-liner straight into your database

Because the output is plain SQL, you can pipe it straight into a client and create a populated table in a single line:

shell
$ ddlgenerator --inserts postgresql mydata.json | psql

3 Supported data formats

Anything that looks like a table of records. The format is detected from the file extension; for inline data it is sniffed automatically.

🐍 Python objects

A list of dicts, a generator, or a single dict. The native input — no file needed.

{ } JSON

Array of objects, or a single object, or an object-of-objects (each becomes a row).

📄 YAML

Lists of mappings. YAML's clean nesting is the nicest way to model hierarchical data.

📊 CSV

Header row becomes column names. First row used for types.

🌐 HTML

The richest table on a page is auto-selected from surrounding noise.

📗 Excel

.xls (xlrd) and .xlsx (openpyxl), multi-sheet.

🍃 MongoDB

Pass a pymongo collection; each document is a row.

🔗 URLs

Fetch remote JSON / YAML / CSV / HTML / Excel with SSRF protection.

Reading from files

When you point at a file, the table is named after the file (minus its extension), and the format is chosen by extension. Here a CSV becomes a PostgreSQL table called animals:

animals.csv
name,species,kg,notes
Alfred,wart hog,22,loves turnips
Gertrude,polar bear,312.7,deep thinker
Emily,salamander,0.3,
sql · postgresql
CREATE TABLE animals (
	name VARCHAR(8) NOT NULL,
	species VARCHAR(10) NOT NULL,
	kg DECIMAL(4, 1) NOT NULL,
	notes VARCHAR(13)
);

INSERT INTO animals (name, species, kg, notes) VALUES ('Alfred', 'wart hog', 22, 'loves turnips');
INSERT INTO animals (name, species, kg, notes) VALUES ('Gertrude', 'polar bear', 312.7, 'deep thinker');
INSERT INTO animals (name, species, kg, notes) VALUES ('Emily', 'salamander', 0.3, NULL);

Notice the inference at work: kg holds both 22 and 312.7, so it became DECIMAL(4, 1) rather than INTEGER; and notes was blank for Emily, so it is the only nullable column — and her row inserts NULL.

JSON & YAML side by side

The same data reads the same way from either format. A JSON menu and a YAML film list, each to a different dialect:

menu.json → sqlite
CREATE TABLE menu (
	name VARCHAR(14) NOT NULL,
	cost DECIMAL(3, 2) NOT NULL,
	warning VARCHAR(13)
);
movies.yaml → mysql
CREATE TABLE movies (
	name VARCHAR(23) NOT NULL,
	rating DECIMAL(2, 1) NOT NULL
);

The menu output shows sparse rows handled gracefully: the third item added a warning column the first two didn't have, so it is nullable and the earlier rows are unaffected.

4 SQL dialects

Any dialect SQLAlchemy speaks. The same data is rendered with the dialect's native types and idiom.

Run the identical inline payload against four databases and watch the string and integer types shift to each engine's preferred form:

postgresql
CREATE TABLE table0 (
	name VARCHAR(6) NOT NULL,
	species VARCHAR(8) NOT NULL,
	kg INTEGER NOT NULL
);
oracle
CREATE TABLE table0 (
	name VARCHAR2(6 CHAR) NOT NULL,
	species VARCHAR2(8 CHAR) NOT NULL,
	kg INTEGER NOT NULL
);
mssql
CREATE TABLE table0 (
	name NVARCHAR(6) NOT NULL,
	species NVARCHAR(8) NOT NULL,
	kg INTEGER NOT NULL
);
sqlite
-- SQLite is permissive with types;
-- VARCHAR(6) / DECIMAL(..) render as
-- affinitized column types.
CREATE TABLE menu (
	name VARCHAR(14) NOT NULL,
	cost DECIMAL(3, 2) NOT NULL,
	warning VARCHAR(13)
);
Accepted dialect names

The positional dialect argument also accepts the friendly spellings pg, pgsql and postgres (→ postgresql), and any prefix of sqlalchemy / django (e.g. sqla, dj).

Beyond raw SQL, two dialects produce code instead of DDL — see ORM models.

5 How it thinks

A few rules explain almost every output. Once you internalize them, the generated DDL is predictable.

① Most-specific type that fits every value

For each column, DDL Generator finds the narrowest type that can hold all of its values. A column of 22 alone is INTEGER; add 312.7 and it widens to DECIMAL(4, 1). Strings are sized to the longest value (with optional cushion).

Heads-up: a lone 0 / 1 is read as BOOLEAN

A column whose only values are 0/1 (or true/false) is inferred as BOOLEAN, not INTEGER. With a single row this can surprise you. The fix is more data — or remap the values so the intent is unambiguous.

② Nullable unless every row has a value

If a key is missing from any row (or empty), the column is nullable. That is why notes above was the only column without NOT NULL.

Sampling changes the inference

Types are inferred from the rows actually read. The --limit flag caps how many rows are inspected, so a limited sample can produce different (narrower) types than the full file. See --limit.

③ Identifiers are normalized

Header names with spaces or mixed case are cleaned into valid SQL identifiers: "common name" → common_name, "Name" → name.

④ The table is named after its source

A file animals.csv yields table animals. A URL yields a name from its path. Inline data with no name falls back to table0 (CLI) or generated_table0 (Python API).

6 Command reference

The command shape is always ddlgenerator [flags] dialect datafile….

usage
ddlgenerator [-h] [-k KEY] [--force-key] [-r] [-u] [-t] [-d] [-i]
             [--no-creates] [--limit LIMIT] [-c CUSHION]
             [--save-metadata-to FILENAME] [--use-metadata-from FILENAME] [-l LOG]
             dialect datafile [datafile ...]
FlagWhat it does
dialectPositional. One of postgresql mysql sqlite oracle mssql, or sqlalchemy/django for ORM code.
datafilePositional (one or more). A file path, URL, SQLAlchemy URL, or inline JSON/YAML string. Multiple files produce multiple tables.
-i, --insertsAppend INSERT statements for every row.
-d, --dropsPrepend DROP TABLE IF EXISTS for idempotent re-runs.
--no-createsEmit only inserts — skip the CREATE TABLE. Pairs with saved metadata for incremental loads.
-u, --uniquesAdd UNIQUE constraints for columns whose values are distinct across the sample.
-t, --textUse unbounded TEXT instead of length-sized VARCHAR(n).
-k, --key NAMEWhen a primary key is needed, name it NAME instead of the default.
--force-keyGive every table a primary key, even if none was otherwise required.
-r, --reorderReorder columns alphabetically, with the key column first.
-c, --cushion NPad variable-length column sizes with extra headroom.
--limit NRead at most N rows from each source (affects inference).
--save-metadata-to FSave the inferred structure to F so later runs can skip re-analysis. (Auto-appends .yaml.)
--use-metadata-from FReuse a previously saved structure instead of re-inferring.
-l, --log LEVELLog verbosity: DEBUG INFO WARN ERROR CRITICAL. Default WARN.
-h, --helpShow help and exit.

7 Flags in action

Each flag demonstrated against real data. All output below is verbatim from the tool.

Including & excluding statements

-d adds the drop, so re-running a script is safe:

shell
$ ddlgenerator -d -i postgresql animals.csv
sql · postgresql
DROP TABLE IF EXISTS animals;

CREATE TABLE animals (
	name VARCHAR(8) NOT NULL,
	species VARCHAR(10) NOT NULL,
	kg DECIMAL(4, 1) NOT NULL,
	notes VARCHAR(13)
);

INSERT INTO animals (name, species, kg, notes) VALUES ('Alfred', 'wart hog', 22, 'loves turnips');
INSERT INTO animals (name, species, kg, notes) VALUES ('Gertrude', 'polar bear', 312.7, 'deep thinker');
INSERT INTO animals (name, species, kg, notes) VALUES ('Emily', 'salamander', 0.3, NULL);

Flip to --no-creates to emit just the inserts (useful for appending to an existing table, or after a metadata-anchored CREATE):

sql · postgresql
INSERT INTO animals (name, species, kg, notes) VALUES ('Alfred', 'wart hog', 22, 'loves turnips');
INSERT INTO animals (name, species, kg, notes) VALUES ('Gertrude', 'polar bear', 312.7, 'deep thinker');
INSERT INTO animals (name, species, kg, notes) VALUES ('Emily', 'salamander', 0.3, NULL);

Detecting uniqueness — -u

For columns whose values are all distinct in the sample, -u emits UNIQUE constraints — handy for natural keys like id and email:

sql · postgresql
CREATE TABLE table0 (
	id INTEGER NOT NULL,
	name VARCHAR(8) NOT NULL,
	UNIQUE (id),
	UNIQUE (name)
);

Unbounded text — -t

Skip the length arithmetic and use TEXT everywhere (great for free-form fields or when you don't want future inserts to overflow a width):

sql · postgresql
CREATE TABLE table0 (
	name TEXT NOT NULL,
	species TEXT NOT NULL,
	kg INTEGER NOT NULL
);

Naming & forcing primary keys

--force-key guarantees a primary key; -k names it. Together they produce a clean surrogate id column:

shell
$ ddlgenerator --force-key -k id postgresql \
    '[{"id": 1, "name": "Alfred"}, {"id": 2, "name": "Gertrude"}]'
sql · postgresql
CREATE TABLE table0 (
	id SERIAL NOT NULL,
	name VARCHAR(8) NOT NULL,
	PRIMARY KEY (id)
);

Alphabetical column order — -r

Reorders columns A→Z, with the key pinned first. Useful for diffing schemas generated from different sources:

sql · postgresql
CREATE TABLE table0 (
	id BOOLEAN NOT NULL,
	apple INTEGER NOT NULL,
	mango INTEGER NOT NULL,
	zebra BOOLEAN NOT NULL,
	PRIMARY KEY (id)
);
Why is id/zebra a BOOLEAN here?

This is the lone-0/1 rule in action: a one-row sample where a column's only value is 1 reads as boolean. More rows would resolve it to INTEGER. It's a faithful illustration of how inference follows the data.

Sizing headroom — -c

Add cushion to give variable-length columns room to grow, so a slightly longer future value still fits:

shell
$ ddlgenerator -c 5 postgresql '[{"Name": "Alfred", "species": "wart hog", "kg": 22}]'
sql · postgresql
CREATE TABLE table0 (
	name VARCHAR(16) NOT NULL,
	species VARCHAR(18) NOT NULL,
	kg BIGINT NOT NULL
);
Cushion can move more than just length

Padding is applied to the inferred column metadata, and in this build it can also nudge the numeric type (kg widened from INTEGER to BIGINT). Treat cushion as "give the schema breathing room" rather than expecting it to touch only strings.

Sampling with --limit

Cap rows read per source — handy for a quick peek at a big file, but be aware it narrows the inference. Here, reading only Alfred's row makes notes appear NOT NULL (Emily's blank value was never seen):

sql · postgresql
CREATE TABLE animals (
	name VARCHAR(6) NOT NULL,
	species VARCHAR(8) NOT NULL,
	kg INTEGER NOT NULL,
	notes VARCHAR(13) NOT NULL
);

INSERT INTO animals (name, species, kg, notes) VALUES ('Alfred', 'wart hog', 22, 'loves turnips');

Many files, one command

Pass multiple datafiles to emit several tables at once — each named after its file:

shell
$ ddlgenerator postgresql movies.yaml menu.json
sql · postgresql
CREATE TABLE movies (
	name VARCHAR(23) NOT NULL,
	rating DECIMAL(2, 1) NOT NULL
);

CREATE TABLE menu (
	name VARCHAR(14) NOT NULL,
	cost DECIMAL(3, 2) NOT NULL,
	warning VARCHAR(13)
);

8 Nested data & child tables

This is DDL Generator's superpower. When a column holds a list or mapping, it splits that nested structure out into its own table and wires up the foreign key.

Each bird ranges over several states. YAML expresses that nesting naturally:

birds.yaml
-
  common name: Northern Cardinal
  scientific name: Carnidalis cardinalis
  length in cm: 21
  state:
    - name: Illinois
      abbrev: IL
    - name: Ohio
      abbrev: OH
-
  common name: Great Northern Loon
  scientific name: Gavia immer
  state:
    - name: Minnesota
      abbrev: MN
sql · postgresql
CREATE TABLE birds (
	common_name VARCHAR(19) NOT NULL,
	scientific_name VARCHAR(21) NOT NULL,
	length_in_cm INTEGER,
	birds_id SERIAL NOT NULL,
	PRIMARY KEY (birds_id)
);


CREATE TABLE state (
	name VARCHAR(14) NOT NULL,
	abbrev VARCHAR(2) NOT NULL,
	birds_id INTEGER NOT NULL,
	FOREIGN KEY(birds_id) REFERENCES birds (birds_id)
);

One parent table birds and one child table state, automatically related. Because a child needs to reference its parent, DDL Generator introduces a surrogate primary key on the parent and logs that it did so:

log
WARNING:root:Primary key birds.birds_id not requested, but nesting demands it
Name the parent key for cleaner DDL

Add -k id and the auto key becomes id instead of birds_id, and the child's foreign key follows suit.

9 Generate ORM models

Use sqlalchemy or django as the dialect and get runnable Python instead of SQL.

sqlalchemy table definitions

The output is a ready-to-run script — engine, metadata, and a Table definition with the same type inference behind it:

shell
$ ddlgenerator sqlalchemy '[{"Name": "Alfred", "species": "wart hog", "kg": 22}]'
python
import datetime
# check for other imports you may need, like your db driver
from sqlalchemy import create_engine, MetaData, ForeignKey
engine = create_engine(r'sqlite:///:memory:')
metadata = MetaData()
conn = engine.connect()

from sqlalchemy import Column, Integer, Table, Unicode


table0 = Table('table0', metadata,
  Column('name', Unicode(length=6), nullable=False),
  Column('species', Unicode(length=8), nullable=False),
  Column('kg', Integer(), nullable=False),
  schema=None)

metadata.create_all(engine)

django models

If Django is installed, the generated DDL is run through Django's inspectdb to produce a model module. (Requires django importable on your path.)

shell
$ ddlgenerator django '[{"Name": "Alfred", "species": "wart hog", "kg": 22}]'
python
# This is an auto-generated Django model module.
# You'll have to do the following manually to clean this up:
#   * Rearrange models' order
#   * Make sure each model has one field with primary_key=True
#   * Make sure each ForeignKey and OneToOneField has `on_delete` set
#   * Remove `managed = False` lines if you wish to allow Django to create/modify/delete the table
from django.db import models


class Table0(models.Model):
    name = models.CharField()
    species = models.CharField()
    kg = models.IntegerField()

    class Meta:
        managed = False
        db_table = 'table0'

10 Working with large tables

DDL Generator loads data into memory, so it is happiest with tables well under your RAM budget. For bigger sets, the intended workflow is analyze once, load many.

The idea: infer the schema from a small representative sample and save it, then generate only INSERTs from the remaining files using that frozen schema — skipping re-analysis entirely.

shell · step 1 — analyze a sample
$ ddlgenerator --save-metadata-to schema.meta postgresql sample.csv
# writes the inferred structure to schema.meta.yaml
shell · step 2 — load the rest without re-analyzing
$ ddlgenerator --no-creates -i --use-metadata-from schema.meta.yaml postgresql batch_2.csv

The saved file is plain, human-readable safe YAML — a columns map of inferred column types plus a children map for any sub-tables. No Python object tags, so it round-trips cleanly through safe_load:

schema.meta.yaml
columns:
  name:
    pytype: builtins.str
    sample_datum: Gertrude
    str_length: 8
    is_nullable: false
    is_unique: true
  kg:
    pytype: decimal.Decimal
    sample_datum: '999.9'
    str_length: 5
    is_nullable: false
    is_unique: true
children: {}

Reusing it reproduces the original schema exactly, then emits the inserts against that frozen definition:

sql · postgresql
INSERT INTO animals (name, species, kg, notes) VALUES ('Alfred', 'wart hog', 22, 'loves turnips');
INSERT INTO animals (name, species, kg, notes) VALUES ('Gertrude', 'polar bear', 312.7, 'deep thinker');
INSERT INTO animals (name, species, kg, notes) VALUES ('Emily', 'salamander', 0.3, NULL);
Same options on both steps

Type sizing (e.g. -c cushion) is applied from the runtime flags at restore time, not baked into the file. Run step 2 with the same flags you used in step 1 so the restored widths match. Child tables are saved under children: and restored with their foreign keys intact.

11 Fetching URLs & scraping HTML

Point the datafile at a URL and DDL Generator fetches it for you — with SSRF protection so it won't reach into private address space.

The format is chosen from the URL's extension; an HTML page triggers table scraping:

shell
$ ddlgenerator postgresql https://example.com/data/cities.html
$ ddlgenerator sqlite https://example.com/data/sales.json

Extracting the table from a noisy page

Web pages are full of layout tables. DDL Generator scores every <table> on the page (favoring tables with many rows, a real header, and several columns) and picks the one most likely to be data. A local Ohio-cities HTML page yields a clean three-column table:

sql · postgresql
CREATE TABLE cities_of_ohio (
	city VARCHAR(22) NOT NULL,
	population VARCHAR(7) NOT NULL,
	county VARCHAR(60) NOT NULL
);
Why is population a VARCHAR?

Because the page contained values like "1,234" (thousands separators) or footnotes that aren't pure integers, so the column was inferred as text. Scrub the source — or post-process the types — if you need a numeric column.

12 Python API

Everything the CLI does is available as a library. The core is the Table class; data is read through Source.

The Table class

Construct it from any iterable of dicts, then ask for SQL, SQLAlchemy code, or inserts in any dialect:

python
from ddlgenerator.ddlgenerator import Table

rows = [{"Name": "Alfred", "species": "wart hog", "kg": 22}]
table = Table(rows)

print(table.sql("postgresql", inserts=True))
output
DROP TABLE IF EXISTS generated_table0;

CREATE TABLE generated_table0 (
	name VARCHAR(6) NOT NULL,
	species VARCHAR(8) NOT NULL,
	kg INTEGER NOT NULL
);

INSERT INTO generated_table0 (name, species, kg) VALUES ('Alfred', 'wart hog', 22);

The same Table constructor accepts the same options as the CLI. The three render methods are:

python
table.sql("mysql")                       # raw DDL (+ inserts/drops via kwargs)
table.sqlalchemy()                       # a runnable SQLAlchemy Table() script
list(table.inserts(dialect="postgresql"))# just the INSERT strings

# options mirror the CLI flags
Table(rows, uniques=True, pk_name="id",
      force_pk=True, reorder=True,
      varying_length_text=True,
      data_size_cushion=5).sql("postgresql")

Reading files with Source

Use Source to read a file, URL, Excel sheet, or MongoDB collection into rows the Table can consume. It doubles as its own iterator and infers a table name:

python
from ddlgenerator.sources import Source
from ddlgenerator.ddlgenerator import Table

with Source("animals.csv") as src:
    table = Table(src, table_name=src.table_name)
    print(table.sql("postgresql", inserts=True))
Use it as a context manager

Source opens files; wrapping it in with ensures they're closed even if generation raises.

13 Security

This modernized fork is hardened compared to the original. The defaults are safe; here's what's under the hood.

🚫 No pickle

Pickle deserialization is removed entirely — there is no .pkl path to exploit.

✅ Safe YAML

Uses yaml.safe_load, so YAML cannot construct arbitrary Python objects.

🛡️ SSRF protection

URL fetching validates destinations and blocks private/internal address ranges.

🔒 Parameterized inserts

Values are emitted as properly bound SQL literals, not interpolated into the query string.

Metadata files are safe too

The saved-schema file is plain safe YAML — column types are stored as names (builtins.str, decimal.Decimal) and resolved back through a fixed whitelist on load, never by importing arbitrary modules. So a tampered metadata file can't name its way into code execution the way a Python-tagged YAML could.

14 Recipes & tips

Common goals, copy-paste ready.

Build a database table from a spreadsheet

shell
$ ddlgenerator -i -d postgresql budget.xlsx > budget.sql
$ psql -f budget.sql

Generate a SQLAlchemy model file

shell
$ ddlgenerator sqlalchemy users.yaml > models.py

Make re-runnable scripts idempotent

-d drops first, so the same script can run over and over:

shell
$ ddlgenerator -d -i sqlite events.json > rebuild.sql

Keep free-text columns unbounded

shell
$ ddlgenerator -t postgresql articles.json

Diff schemas generated from different sources

Normalize column order so diffs are stable:

shell
$ ddlgenerator -r --force-key -k id postgresql prod_dump.json

Read a multi-sheet workbook

Excel sources iterate every sheet by default; each sheet becomes its own table (named workbook-sheet).

Gotcha: inline data needs quotes

When passing JSON/YAML directly on the command line, quote the whole string so your shell doesn't touch the braces and spaces: '[{"a": 1}]'.

15 Troubleshooting

ImportError: must pip install openpyxl / xlrd / ...

You hit a format whose parser isn't installed. Install the matching extra — [html], [excel], or [mongo].

NotImplementedError: First arg must be one of: ...

The dialect wasn't recognized. Use one of postgresql mysql sqlite oracle mssql sqlalchemy django (or the friendly aliases / prefixes noted in Dialects).

A column came out as BOOLEAN / TEXT when I expected INTEGER / VARCHAR

That's inference following the data, not a bug. A lone 0/1 → BOOLEAN; values with commas or units → VARCHAR. Fix the source data, add more rows, or remap the column afterward. See How it thinks.

A column I expected to be NOT NULL came out nullable (or vice-versa)

Nullability is decided by which rows were actually read. If you used --limit or a sparse sample, widen the sample. A value missing in any read row makes the column nullable.

--use-metadata-from complains the saved file is the wrong name

--save-metadata-to automatically appends .yaml, so --save-metadata-to schema.meta writes schema.meta.yaml. Reference the actual filename when restoring: --use-metadata-from schema.meta.yaml.

ValueError: Unknown column type ... in metadata file

The metadata file named a type that isn't on ddlgenerator's whitelist (e.g. it was hand-edited or comes from an incompatible version). Re-generate the file with --save-metadata-to from a current run; the type is resolved through a fixed whitelist, so an unknown name is refused rather than imported.

The generated SQLAlchemy output references undefined metadata

The script declares engine and metadata for you at the top; just make sure you keep those lines when you copy the Table(...) definition into your own project.
